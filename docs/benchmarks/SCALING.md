# Kernel-time and grade scaling (Stage 14b)

Report §9.5.1 (reference configuration, measured values only), §5.1.3; docs/tasks/STAGE14_TASK.md B1–B2. Generated by `scripts/bench_scaling.py report` from `docs/benchmarks/scaling.csv` (raw results in the git-ignored `bench/scaling/out/`); no number is hand-edited. Sources: `bench/scaling/*.cqr` (`scripts/gen_scaling.py`, fixed seeds).

## Method

- Machine: 13th Gen Intel(R) Core(TM) i9-13900H; 20 logical CPUs; 2600 MHz; RAM 16108 MB; Microsoft Windows 11 Home Single Language 10.0.26200; `LEAN_NUM_THREADS=4` (as recorded in the certificates of the certify phase; the time and committed phases ran in the same shell).
- Toolchain: leanprover/lean4:v4.35.0, Mathlib 56a005855ea1, Physlib 96a6bc5e3c50.
- Per instance and iteration count: `cqr certify <src> --solutions M --iterations r` (timeout 900 s; M from the truth table of the network, cross-checked against the reference predicate on every input; for n ≤ 12 the certificate decides M by the kernel, `hM_count`, for n > 12 it is the hypothesis `hM_card`), then 6 interleaved runs of `lean -Dprofiler=true Cert.lean` in round-major order (the instances alternate), the first run excluded: kernel time = the profiler's `type checking`, min and median of the remaining runs; wall time = median wall of those runs; peak memory = peak working set of the lean process (Windows `GetProcessMemoryInfo`). Outcome: `certified`, `timeout` (900 s), `oom`, `error`.
- Harness (CLAUDE.md rule 9) on the synthesized oracle of every n ≤ 12 instance, with the reference predicate (never the network): every measurement branch when a ≤ 6 and n + a ≤ 20, otherwise Born-sampled branches when n + a ≤ 20 (the simulator's MAX_QUBITS), otherwise `infeasible` (the statevector holds all n + a qubits). The grade of an instance whose harness verdict is not `pass` is reported with the mark † (kernel-checked certificate, no statevector check). ‡ = the synthesizer's grade written to Cert.lean (`grade_eq`) for an instance whose kernel check did not finish: planned, not certified.
- Grades are measured on the emitted circuit (the certificate's `grade_eq`); `instructions` = gates of the `emitted` literal (alloc/free included); G = noisy operations of `δ_hw ≤ δ + G·p̄` (terminal measurements included); AND / XOR = nodes of `net`.

The largest peak working set of a kernel-decided certificate is **11371 MB (11.1 GB) for carry_5_r1 (n = 10)** on a machine with 16108 MB (15.7 GB) of RAM.
At n = 12, 6 of 6 kernel-decided certificates did not finish (carry_6_r1 timeout, rand_a4_r1 timeout, rand_a8_r1 timeout, rand_a8_r3 timeout, rand_a32_r1 timeout, rand_a64_r1 timeout); the `_h` form of the same instance (M as the hypothesis `hM_card`, `--count-limit 0`) is in the tables above where it finished. The count `hM_count` evaluates `Network.pred` on 2^n inputs inside the kernel; its working set at n = 10 already takes most of this machine's RAM, and 2^12 is four times 2^10. The kernel time of the kernel-decided certificates also grows fast with n (carry_4 → carry_5: 10.60 s → 103.00 s median, ×9.7 for 2 more input bits), so from the time trend alone a 900 s timeout at n = 12 is expected; with the memory trend both bind, and which binds first is not measured because the peak of a timed-out run is not recorded (the certify phase keeps the peak of finished runs only). **Recommendation (no change in this stage): revisit the default `--count-limit 12` of `cqr certify` (Stage 14a). The largest kernel-decided certificate that finished is carry_5 (n = 10, 103.00 s median, 11371 MB); no n = 12 one finished. A default of 10, or a default tied to the network size, with the `_h` form as the fallback.**
