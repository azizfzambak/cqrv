
and line 449 of that file is `theorem grade_eq : Synthesis.grade emitted = ⟨76, 585, 300, 64⟩ := by decide +kernel`. `emitted_ok` (line 442, `decide +kernel` on the 1953-gate literal against the synthesizer's output) and `nAnc_eq` (line 451) passed in the same run. The Stage 14b/14c texts, `SCALING.md` and the roadmap attributed the failure to the emitted literal; the correct attribution is the kernel evaluation of the scheduler inside `Synthesis.grade` (`SCALING.md` is generated and stays as it was; this file and DECISIONS.md carry the correction). The recursion came from the representation of the scheduler state: `SchedState.placed : Array (Gate × Nat)` built by one `Array.push` per gate, i.e. one nested `List.concat` per gate inside the kernel's term, unfolded by the first traversal of the finished schedule (`depth`'s fold) — a 1953-deep chain, which `--tstack` (14c) could not move because it is the kernel's own recursion guard, not the thread stack.

With the state as a cons list and `schedule := ⟨placed.reverse⟩` (one tail-recursive reverse), **no recursion error appears at any size tried**: carry_7 (612 instructions) and carry_8 (706) certify, and rand_a64 at 1953 ran for the full 900 s inside `cqr certify` without stopping (in Stage 14b the same file failed after 69 s with the error above). In every profiled certificate only three declarations rise above the 1 s threshold: `grade_eq`, `gradeExt_eq` and, where the count is kernel-decided, `hM_count`. `emitted_ok` — the kernel re-running the synthesizer on `net` and comparing with the literal — stays below 1 s at 706 instructions (and passed at 1953 in 14b), as do `net_ok`, `front_end`, the oracle / MCZ certificates and `cert`. Hypothesis for the growth (no new experiment): `decide +kernel` makes the kernel reduce `Decidable.decide (Synthesis.grade emitted = ⟨…⟩)` by whnf, and the kernel memoises every intermediate whnf / defeq result of one declaration in caches that live until the declaration is accepted. The scheduler's fold produces, per gate, a fresh state term (the two association lists rebuilt by `filter`, the `ready` term as a chain of `Nat.max` over lookups), and every projection, lookup and comparison on those terms is a cached entry; the number of distinct intermediate terms is of the order gates × (width + bits) for `grade` and depth × gates for `tDepth` — tens of millions of cache entries of some hundred bytes each at 700 gates. The elaborator evaluates the same `decide +kernel` once more at elaboration time in the same process (the per-declaration profiler figure is about twice the certificate's metric, Stage 17b), so two such caches coexist briefly. The literal `emitted` itself is not the problem: `emitted_ok` evaluates the synthesizer and compares 1953 gates by `decEq` in under a second.

### A0 — the `Nat m` item (Stage 16b review, decision 4)

Not reproducible through `cqr certify`, for two reasons visible in the code: the extractor classifies only a program with exactly one `Vec` parameter and a `Bool` result as Search (`CQRV/DSL/Extract.lean`, `isSearch`), so any program with a `Nat m` parameter is a Decision problem, the matcher gives the Grover hint and `cqr certify` writes nothing (recorded above, exit 1 in 0.04 s); and the typed syntax has no `Nat → Bool` operation (no comparison; `idx` takes a literal or a `for` index), so a Boolean predicate cannot read a `Nat` value at all — the only consumers are a `Nat`-typed `if` / `let` or a `Nat` result. The front-end block a certificate would carry (`net`, `prog`, `prog_scoped` by `decide`, `net_ok` by `decide +kernel`, `front_end`), written by the new `CertifyTool front-end` for `nat_m` (`Vec Bool 4 × Nat 3`), `nat_ret` (a `Nat 3` result), `nat_wide` (`Nat 65536`, 16 bits) and `for_idx` (a `for` index read as a value), costs 0.02 / 0.01 / 0.35 / 0.12 s of kernel time and under 0.5 s of elaboration per declaration — the same as the Vec-only baseline (0.03 s). The Stage 16b observation ("over five minutes for a scratch program with a `Nat 3` parameter") therefore did not come from this block as `cqr certify` produces it; it must have come from a hand-built request or from a different declaration (the kernel-decided count `hM_count` on a wider network, or an elaboration under a different setting), and it cannot occur in any certificate the tool writes today. Recommendation for the 18a review: close the item; if a `Nat` parameter is ever admitted to the Search class, re-run `scripts/kernel_forms.sh --only natm` first.

### Recommendation for the Stage 19–20 certificate form (a recommendation, not a decision; the reviewer decides at the 18a review)

The question is the kernel evaluation of the scheduler, not the emitted literal. The running example at precision m = 4 is about 15 controlled Grover iterations, roughly 10 000 gates; every certificate must check on a 16 GB machine, whatever machine measures.

- **Flat literal with `decide +kernel` as today**: out. Memory exceeds 8 GB at 838 gates and the growth is superlinear; no setting of this toolchain changes it.
- **(a) A kernel-friendly evaluator** `gradeK` / `gradeExtK`, proved equal to `Circuit.grade` / `Circuit.gradeExt` once by a general theorem, so that `grade_eq` stays an exact equality about the real definition: worth having, but it buys a constant factor only. The scheduler's work is inherently gates × (qubits touched) with association lists of length ≤ width, and whatever the evaluator does, the kernel caches its intermediate terms per declaration; replacing the `filter`-rebuilt lists by fixed-width lists updated in place, computing `depth` inside the fold (no second traversal) and `tDepth` as a running set of T layers (instead of depth × gates `any`) removes most of the garbage but not the quadratic shape (`List` access is linear in the kernel; there are no arrays). My estimate is a 2–5 × gain in both time and memory, i.e. roughly 1 500–2 500 gates under 8 GB. That does not reach 10 000 gates; it does enlarge the blocks of (b).
- **(b) A compositional form** — `countingCircuit n m P` assembled from certified blocks (the controlled oracle, the controlled diffusion, the inverse (A)QFT), each block measured exactly as today (`grade_eq` / `gradeExt_eq` per block at ≤ ~600 gates, hence ≤ ~6 GB each, sequential declarations whose memory is released one after the other), the whole circuit's `Grade` from the block grades through the ⊕ / ⊗ monoid of report §3.1 (an **upper bound** in the budget order, not the measured value — the certificate must say so, and the realization statement must be stated against a bound, which is how §3.1.3 composes; to confirm in 19a that the Stage 20b lemma takes the grade as a bound), the additive components of `GradeExt` (`twoQ`, `rot`, `meas`, `ff`) exactly and `tDepth` as a bound (sum of the block T-depths; `GradeExt` has no algebra by the Stage 17a decision, so this is a new, small statement), the hash link per block and the assembly by `rfl` / `decide` on list appends (cheap: `emitted_ok` at 1953 gates was under a second). Sizes: for the running example every block is far below 600 gates (the oracle is 39 gates, one Grover iteration about 200, their controlled versions perhaps twice that; the inverse QFT on 4 qubits 10 gates), so this form stays under 8 GB by a wide margin and scales with the number of blocks, not with the total gate count. **This is my recommendation**, with (a) as an optional improvement of the per-block measurement.
- **(c) A layer witness from the untrusted scheduler, checked in one pass**: the certificate carries the layer of every gate (and, to make the check local, the index of each gate's predecessor on each of its qubits); the kernel checks that every layer is one more than the maximum over the predecessors and that the predecessor pointers are consistent. The check needs no association lists, but a pointer into a 10 000-element `List` costs a linear walk in the kernel, so the one pass is still quadratic with smaller constants — I would expect it to sit between the flat form and (a) in memory and to need a proof that the witness check implies `schedule`'s layers (a new theorem about the scheduler, larger than (a)'s equality). Not recommended as the primary route; it becomes attractive only if the kernel gains array literals.

If the reviewer prefers an exact measured grade for the whole 10 000-gate circuit, the only route I see is (a) pushed hard plus a measuring machine with far more than 16 GB — and that contradicts the constraint that every certificate checks on 16 GB. (b) keeps the 16 GB constraint by construction.
